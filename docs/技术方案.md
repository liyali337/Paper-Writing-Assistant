# 深度学习实验智能体 技术方案

产品方案文档位于 `docs/`。开源对照在 `refs/`，不参与构建。

## 1. 背景与目标

仓库 `Paper-Writing-Assistant` 当前为空目录，无既有代码、依赖或运行时约束。本方案按绿场系统设计，目标是落地一个**深度学习实验智能体平台**：围绕用户的具体项目，完成文献吸收、方法提案、代码修改、实验启动、结果评估与迭代优化。

用户价值：把“读论文 → 想方法 → 改代码 → 跑实验 → 看结果 → 再优化”从人工串行，变成可审计、可回滚、可中断恢复的智能体闭环。

成功标准：

- 用户可上传 PDF，并按项目上下文检索到带引用的证据片段。
- 系统每日自动拉取相关论文，生成与当前项目可对齐的方法候选。
- 智能体可在沙箱内改代码、提交实验、读取指标，并基于结果提出下一轮改动。
- 所有高风险动作（写代码、启动 GPU 任务、覆盖已有结果）可追踪、可审批、可回滚。

## 2. 范围与非目标

### 2.1 范围（In Scope）

- Agent Runtime / Harness：prompt 组装、tool / function call 循环、预算与中断。
- 能力接入：本地 Tool、MCP Server、Skills 包。
- 知识层：PDF 入库、RAG、项目画像、实验记忆。
- 文献层：按主题/项目每日检索 arXiv / Semantic Scholar 等来源。
- 实验层：方法提案、代码补丁、任务提交、指标评估、优化建议。
- 编排层：用 LangGraph 管理多阶段实验闭环状态机。
- 文档处理层：用 LangChain 生态组件做 PDF 解析、切分、检索链，不把 LangChain 当 Agent 大脑。

### 2.2 非目标（Out of Scope，MVP 及 v1 明确不做）

- 不替代训练框架本身（不自研新的 PyTorch / JAX 内核）。
- 不承诺跨集群调度器的完整实现（SLURM / K8s 仅预留 Runner 适配器）。
- 不自动投稿、不自动生成虚假实验结果。
- 不在无审批情况下对远程生产集群做破坏性操作。
- 不把所有能力塞进单一巨型 Prompt；Skills / Tools / MCP 必须可拆可测。

## 3. 现状与主要痛点

### 3.1 现状

- 仓库为空，无模块、无接口、无数据模型、无 CI。
- 可复用模式需本方案一次性约定：Python 3.11+、FastAPI、PostgreSQL、对象存储、向量库、Git 工作区。

### 3.2 痛点（若不做分层，后续必然出现）

- 概念堆叠：prompt / tool / function call / MCP / skills / RAG / harness / 上下文 / LangChain / LangGraph 若平铺进一个 Agent 类，会变成不可测试的超级循环。
- 长任务与短对话混用：论文检索是分钟级，训练是小时到天级，不能共用一次 LLM 会话超时。
- 代码修改不可逆：没有 snapshot / patch / rollback，实验智能体无法安全落地。
- 知识与项目脱节：通用论文库无法回答“对我这个模型/数据集是否可行”。
- 结果不可审计：缺实验 run id、prompt 版本、使用过的证据、代码 diff、指标对照。

## 4. 方案候选对比（2-3个）

### 候选 A：LangChain Agent 全家桶

- **核心思路**：用 LangChain AgentExecutor 串联 tools，用 Retriever 做 RAG，用定时任务拉论文。
- **影响模块**：几乎全部能力都写在 Chain / Tool 包装里。
- **数据/接口变化**：业务对象被 Chain 输入输出字典稀释，实验状态难以持久化。
- **风险与成本**：抽象泄漏高，长循环（跑实验、等 GPU）与对话循环冲突；LangChain 大版本迁移成本高。
- **适用边界**：适合 Demo、单轮问答、一次性 RAG 问答，不适合多日实验闭环。

### 候选 B：纯自研 Runtime，不用 LangChain / LangGraph

- **核心思路**：自写 tool loop、工作流引擎、文档解析与向量检索。
- **影响模块**：Harness、工作流、RAG、调度全部自建。
- **数据/接口变化**：契约最干净，但基建工作量大。
- **风险与成本**：PDF 解析、切分、重试图、checkpoint 都要自研，延期风险高。
- **适用边界**：团队已有成熟 Agent 内核时才划算。当前为空仓库，不适合。

### 候选 C：自研 Harness + LangGraph 状态机 + LangChain 仅作 RAG 组件（推荐）

- **核心思路**：把“智能体内核”和“实验工作流”和“文档处理”分成三层。LangGraph 只管有状态的实验闭环；LangChain 只提供 loaders / splitters / retrievers；MCP 与 Skills 作为能力插件；Harness 负责模型调用、上下文装配、工具循环、预算与审计。
- **影响模块**：`harness`、`graph`、`knowledge`、`research`、`workspace`、`runner`、`eval`。
- **数据/接口变化**：以领域对象为中心（Project、Paper、Evidence、Patch、Run、Metric、Decision），Graph 只存这些对象的引用。
- **风险与成本**：中等。需要自己定义清晰的接口，但可复用成熟组件，实验闭环可控。
- **适用边界**：需要长期运行、可回滚、可审计的科研实验助手。

## 5. 推荐方案与取舍理由

采用**候选 C**。

理由：

1. **不是其他候选的原因**：A 把控制权交给 Chain，无法稳定承载“提交训练 → 等结果 → 再改代码”；B 重复造轮子，空仓库交付周期不可接受。
2. **深模块原则**：对外只暴露少量接口（`ingest_pdf`、`daily_research`、`propose`、`apply_patch`、`submit_run`、`evaluate`、`iterate`），内部封装 prompt、检索、MCP、调度。
3. **概念各就其位**，避免同义重复：
   - **Prompt**：系统策略 + 项目画像 + 当前阶段指令，由 Harness 组装，不散落在各 Tool 里。
   - **Function Call / Tool**：模型可调用的函数，统一 JSON Schema，执行走 Tool Router。
   - **MCP**：把外部系统（arxiv、文件系统、实验集群、Git）变成标准工具源，不在业务里写死 SDK。
   - **Skills**：可版本化的标准作业程序（SOP），例如“读 PDF 并抽取方法对照表”“根据 val loss 做消融设计”，不是又一套 Tool。
   - **RAG**：只负责证据召回与引用，不负责决策。
   - **Harness**：运行时内核（循环、上下文窗口、重试、权限、审计）。
   - **Context**：分层记忆，而不是把所有历史塞进一次 prompt。
   - **LangChain**：文档 ETL / 检索组件。
   - **LangGraph**：实验闭环状态机与 checkpoint。

## 6. 详细设计

### 6.1 模块与职责（含接口边界）

```text
                    ┌─────────────────────────────────────────┐
                    │              API / CLI / UI             │
                    └───────────────────┬─────────────────────┘
                                        │
                    ┌───────────────────▼─────────────────────┐
                    │         Agent Harness（内核）            │
                    │  prompt组装 / tool循环 / 预算 / 审计     │
                    └─┬───────────┬───────────┬───────────────┘
                      │           │           │
           ┌──────────▼┐  ┌───────▼──────┐  ┌─▼──────────────┐
           │SkillRegistry│  │ MCP Gateway │  │ Context Store  │
           └──────────┬┘  └───────┬──────┘  └─┬──────────────┘
                      │           │           │
        ┌─────────────▼───────────▼───────────▼──────────────┐
        │              LangGraph Experiment Graph            │
        │  research → propose → patch → run → eval → iterate │
        └─┬─────────┬─────────┬─────────┬─────────┬──────────┘
          │         │         │         │         │
     Knowledge  Research  Workspace   Runner    Evaluator
     (RAG/PDF)  (论文雷达)  (代码补丁)  (实验任务)  (指标/报告)
```

#### 模块清单（深模块，接口少、实现藏在内部）

| 模块 | 职责 | 对外接口（最小集） | 不该做的事 |
|---|---|---|---|
| `harness` | 模型调用、prompt 组装、function call 循环、token/费用预算、中断 | `run_turn()`, `run_tool_loop()` | 解析 PDF、提交 GPU 任务 |
| `context` | 分层上下文：系统、项目、证据、实验、工作区 | `assemble()`, `pin()`, `evict()` | 直接调 LLM |
| `skills` | 加载 `SKILL.md` + 脚本，按阶段注入 | `get(name)`, `render(name, vars)` | 自己执行高风险副作用 |
| `mcp_gateway` | 发现/鉴权/调用 MCP tools，映射为内部 ToolSpec | `list_tools()`, `call(tool, args)` | 业务决策 |
| `knowledge` | PDF 入库、切分、embedding、引用检索 | `ingest()`, `query()` | 生成实验方案 |
| `research` | 每日论文拉取、去重、与项目对齐打分 | `watch()`, `harvest()`, `rank()` | 改用户代码 |
| `workspace` | Git 工作副本、补丁应用、语法检查、回滚 | `snapshot()`, `apply_patch()`, `rollback()` | 直接 SSH 到训练机乱写 |
| `runner` | 实验任务提交、日志、状态、产物 | `submit()`, `status()`, `cancel()`, `artifacts()` | 解释指标好坏 |
| `evaluator` | 指标对比、失败归因、下一轮假设 | `compare()`, `diagnose()` | 无证据地宣称 SOTA |
| `graph` | LangGraph 状态机、checkpoint、人工门禁 | `start_cycle()`, `resume()`, `approve()` | 塞进具体解析逻辑 |

已自动确定的技术选型（空仓库，直接落定）：

- 语言：Python 3.11+
- API：FastAPI
- 工作流：LangGraph + Postgres checkpointer
- RAG 组件：LangChain document loaders / text splitters；向量库 Qdrant
- 元数据：PostgreSQL
- 对象存储：本地文件系统起步，接口按 S3 兼容预留
- 队列：Redis + 后台 worker（论文抓取、embedding、实验轮询）
- 工作区：每项目一个 git worktree
- 实验追踪：先接 MLflow（本地可跑）；W&B 作为可选 sink
- 模型接入：OpenAI 兼容接口（`base_url` + `api_key`），便于切换本地 / 云端模型

### 6.2 关键流程与异常路径

#### 6.2.1 主闭环（每日或用户触发）

```text
[ProjectProfile]
    → Research.harvest(topics derived from profile)
    → Knowledge.query(project + new papers)
    → Graph.propose(methods scored by feasibility)
    → 人工或策略门禁（默认：改代码前需确认）
    → Workspace.apply_patch
    → Runner.submit
    → 轮询至终态或超时
    → Evaluator.compare(baseline, current)
    → 生成 Decision：keep / revert / next_hypothesis
    → Context 写入 ExperimentMemory
```

LangGraph 节点：

1. `load_project`
2. `retrieve_evidence`
3. `propose_methods`
4. `gate_approval`（可配置 auto / require_human）
5. `patch_code`
6. `static_check`（测试、import、配置校验）
7. `submit_run`
8. `await_run`
9. `evaluate`
10. `iterate_or_stop`

每个节点失败进入 `compensate`：记录错误、保留现场、不自动覆盖 baseline。

#### 6.2.2 PDF 入库

1. 上传 PDF → 对象存储。
2. LangChain loader 抽取文本 + 页码。
3. 按标题/段落/公式感知切分（chunk 带 `paper_id`, `page`, `section`）。
4. Embedding 写入 Qdrant；元数据写入 Postgres。
5. 失败：解析失败标 `ingest_failed`，允许用户重试或改用 OCR 通道（v1 后）。

#### 6.2.3 每日论文雷达

1. 定时任务（默认 每天 06:00 用户时区）按 Project 的 query 模板检索。
2. 去重（arxiv_id / doi / 标题归一化）。
3. 与项目画像做相关性 + 可复现性打分（有代码、有数据集、方法类型匹配）。
4. 高分论文自动入库 RAG；生成「今日简报」。
5. 抓取失败：指数退避，不阻塞实验图。

#### 6.2.4 代码修改与实验启动（高风险路径）

1. `workspace.snapshot()` 生成 `git commit`（agent 分支）。
2. 模型只输出 **unified diff**，不整文件重写。
3. `apply_patch` 后跑静态检查与用户定义 smoke test。
4. 检查失败 → 自动 rollback，并把失败日志作为下一轮上下文。
5. 检查通过 → `runner.submit`，写入 `run_id`。
6. 运行失败（OOM / CUDA / 数据路径）→ Evaluator 归类，禁止无限制重试（默认最多 2 次同类失败）。

#### 6.2.5 异常与停止条件

- Token / 费用超预算：Harness 停，状态 `budget_exceeded`。
- 实验超时：Runner 标记 `timeout`，不杀用户手动任务（可配置）。
- 指标相对 baseline 劣化超过阈值：默认 revert patch，记录 negative result。
- 人工 `cancel`：Graph 在最近 checkpoint 停止，不删除历史 run。

### 6.3 接口与数据契约

#### 6.3.1 核心领域对象

```python
class ProjectProfile:
    project_id: str
    root_path: str
    task_type: str            # e.g. "image-classification"
    framework: str            # e.g. "pytorch"
    dataset: str
    constraints: dict         # GPU, 时长, 禁止改动的文件
    baseline_run_id: str | None
    research_queries: list[str]

class Evidence:
    evidence_id: str
    source: str               # pdf | arxiv | run_log | code
    locator: str              # page / url / file:line
    text: str
    score: float

class MethodProposal:
    proposal_id: str
    title: str
    rationale: str
    evidence_ids: list[str]
    expected_gain: str
    risk: str
    patch_plan: list[str]
    feasible: bool

class CodePatch:
    patch_id: str
    diff: str
    files: list[str]
    snapshot_sha: str

class ExperimentRun:
    run_id: str
    project_id: str
    patch_id: str | None
    status: str               # queued|running|succeeded|failed|timeout|cancelled
    metrics: dict[str, float]
    artifacts_uri: str | None
    logs_uri: str | None

class Decision:
    keep: bool
    revert: bool
    next_hypothesis: str | None
    reason: str
    evidence_ids: list[str]
```

#### 6.3.2 HTTP 最小集

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/projects` | 注册项目根目录与约束 |
| POST | `/knowledge/pdfs` | 上传 PDF |
| GET | `/knowledge/search` | RAG 检索 |
| POST | `/research/harvest` | 手动触发论文雷达 |
| GET | `/research/digest` | 今日论文简报 |
| POST | `/cycles` | 启动一轮实验图 |
| POST | `/cycles/{id}/approve` | 批准改代码 / 跑实验 |
| GET | `/cycles/{id}` | 状态、checkpoint、当前节点 |
| POST | `/runs/{id}/cancel` | 取消实验 |
| GET | `/runs/{id}` | 指标与日志引用 |

内部 Tool Schema 与 HTTP 对齐，避免两套语义。例如 Tool `knowledge.query` 的返回必须是 `list[Evidence]`，不得返回自由文本冒充证据。

#### 6.3.3 Prompt / Tool / Skill / MCP 的装配契约

Harness 每次调用模型前组装：

```text
[System Policy]          # 安全、引用、禁止伪造指标
[Skill Pack]             # 当前阶段 SKILL.md 正文
[Project Profile]        # 压缩后的项目画像
[Pinned Evidence]        # RAG 命中，带 locator
[Experiment Memory]      # 最近 N 次 run 的指标摘要
[Working Set]            # 当前文件树、diff、报错
[Tool Specs]             # function call JSON Schema
[User / Graph Instruction]
```

规则：

- RAG 结果进入 `Pinned Evidence`，不进 System。
- Skill 只在对应 Graph 节点注入，例如 `propose_methods` 才加载「方法可行性评估」Skill。
- MCP tools 经 Gateway 转成与本地 Tool 相同的 `ToolSpec`，模型无感知来源差异。
- Function call 执行后，观测结果写回 Context，而不是追加无限聊天记录。超限时按优先级驱逐：Working Set > 旧对话 > 低分 Evidence；Project Profile 与 Policy 永不驱逐。

### 6.4 存储与迁移策略（如涉及）

当前无历史数据，无迁移。表结构从第一天按可演进设计：

- `projects`, `documents`, `chunks`, `papers`, `proposals`, `patches`, `runs`, `decisions`, `audit_logs`
- Qdrant collection：`kb_chunks`（payload 含 `project_id`，检索必须过滤项目，禁止串库）
- LangGraph checkpoint：Postgres（支持进程重启后 resume 等待中的实验）
- 代码快照：git 对象，不把完整仓库拷进 Postgres
- 产物：`artifacts/{project_id}/{run_id}/`

版本约定：embedding 模型变更时新建 collection，不原地覆盖；检索时记录 `embedding_model` 版本。

### 6.5 安全、权限与脱敏

- **默认拒绝**：未在 Project `constraints.allowlist` 内的路径不可写。
- **门禁**：`apply_patch` 与 `submit_run` 默认 `require_human=true`；仅当项目开启 `auto_pilot` 且预算未超时才自动执行。
- **密钥**：模型 key、W&B token、集群凭证只进环境变量 / 系统钥匙串，禁止进入 prompt 与日志。
- **日志脱敏**：过滤 `api_key`、`Authorization`、home 路径中的 token 文件内容。
- **MCP**：按项目启用 server 白名单；文件系统 MCP 根目录绑定 `project.root_path`。
- **结果诚实性**：Evaluator 只读取 Runner / MLflow 的结构化指标；禁止模型“口算”出最终数字写入 `ExperimentRun.metrics`。
- **论文版权**：PDF 仅私有知识库，不对外同步；抓取遵守来源 ToS 与速率限制。

### 6.6 可观测性（日志/指标/追踪）

结构化日志字段（全程必带）：`trace_id`, `project_id`, `cycle_id`, `node`, `run_id`, `tool_name`。

关键日志点：

- Harness 入/出：模型名、token 用量、tool 名、耗时。
- Knowledge：ingest 页数、chunk 数、query topk 与空结果。
- Graph：节点转移、checkpoint 写入、门禁等待。
- Runner：submit、状态变化、失败原因码（OOM/CUDA/data/timeout）。
- Evaluator：baseline vs current 的 delta。

指标：

- `agent_tool_calls_total{tool,status}`
- `agent_token_usage{model,stage}`
- `kb_ingest_seconds`
- `run_duration_seconds{status}`
- `cycle_success_ratio`

追踪：每个 cycle 一条 root span，节点与 tool 为子 span。本地用 OpenTelemetry → 文件 / Jaeger（可选）。

## 7. 风险、依赖与回滚

| 风险 | 影响 | 缓解 | 回滚 / 兜底 |
|---|---|---|---|
| PDF 解析质量差（双栏、公式） | RAG 证据不可用 | 保留页码；失败标记；后续加 OCR | 用户改用纯文本/markdown 补充 |
| 论文抓取被限流 | 每日简报空洞 | 多源 + 缓存 + 退避 | 手动上传 PDF 仍可用 |
| 模型乱改代码 | 实验不可复现 | diff-only、allowlist、smoke test、默认人工批准 | `workspace.rollback(snapshot_sha)` |
| 长训练把 Graph worker 拖死 | 服务不可用 | `await_run` 只轮询，不占用 LLM 循环 | 进程重启后从 checkpoint resume |
| LangChain / LangGraph API 变动 | 升级失败 | 仅在 `knowledge` 与 `graph` 两处依赖，做适配层 | 适配层内钉版本 |
| 伪造指标 | 错误科学结论 | 指标只从 MLflow/Runner 读 | 报告展示 raw metric source |
| GPU 资源争用 | 任务排队或杀死 | Runner 配额与队列 | cancel 不影响已成功 run |

依赖：Python 3.11、PostgreSQL、Redis、Qdrant、Git、可用的 LLM endpoint；实验机需能被 Runner 适配器访问（MVP 为本机 subprocess）。

## 8. 测试与验收标准

### 8.1 模块测试（必须可单测，不启真实 GPU）

- `knowledge.query`：给定固定 chunk fixture，断言返回带 `locator` 的 Evidence。
- `workspace.apply_patch`：合法 diff 可应用；越出 allowlist 被拒绝；失败自动回到 snapshot。
- `harness`：对 mock 模型做两轮 function call，断言预算截断。
- `evaluator.compare`：只接受结构化 metrics，忽略模型自然语言里的数字。
- `mcp_gateway`：把一次 MCP tool 调用映射为内部 ToolResult，错误码不丢。

### 8.2 图测试

- 用 LangGraph 内存 checkpointer 跑通：propose → 拒绝门禁 → 不调用 runner。
- 批准后门禁：patch 失败则到达 compensate，且 `rollback` 被调用。
- `await_run` 收到 `succeeded` 后进入 evaluate，并写出 Decision。

### 8.3 端到端验收（MVP）

1. 注册一个最小 PyTorch 项目（例如 MNIST 训练脚本）。
2. 上传 1 篇相关 PDF，检索能命中文中某页原句。
3. 手动触发 harvest，至少写入 1 篇带 arxiv_id 的论文元数据（可用 mock server）。
4. 启动 cycle，智能体提出 1 个可执行提案（含 evidence_ids）。
5. 批准后生成 patch，smoke test 通过，Runner 提交并返回 `run_id`。
6. 用假指标文件完成 evaluate，生成 keep/revert 决策与报告。
7. 全程 `audit_logs` 可按 `cycle_id` 查出 prompt 版本、工具调用、diff、指标来源。

## 9. 实施步骤与里程碑

### M0 骨架（约 1 周）

- 目录：`src/dl_agent/{harness,context,skills,mcp_gateway,knowledge,research,workspace,runner,evaluator,graph,api}`
- Postgres / Redis / Qdrant docker-compose
- 空实现 + 契约测试打红，保证接口先于实现

**交付物**：可启动的 API 与模块边界。  
**验收**：导入与健康检查通过。

### M1 知识库 + RAG（约 1 周）

- PDF ingest、切分、embedding、项目内检索
- LangChain 仅出现在 `knowledge` 适配层

**交付物**：`POST /knowledge/pdfs`、`GET /knowledge/search`  
**验收**：第 8.3 条 2。

### M2 Harness + Tools + Skills + MCP（约 1.5 周）

- function call 循环、预算、审计
- 内置 tools：`kb.query`、`fs.read`、`git.diff`
- 1 个 MCP server 样例（arxiv search）
- 2 个 Skills：`paper-method-extract`、`experiment-hypothesis`

**交付物**：可对话的 Agent，但还不能提交训练。  
**验收**：tool 循环单测 + 审计日志。

### M3 工作区补丁 + 本地 Runner（约 1.5 周）

- git snapshot / patch / rollback
- 本机实验 subprocess + MLflow 指标读取
- 门禁 approve

**交付物**：安全改代码并跑短实验。  
**验收**：第 8.3 条 4–6（可用短训练或 mock run）。

### M4 LangGraph 闭环 + 每日论文雷达（约 1.5 周）

- 完整 graph 与 checkpoint resume
- 定时 harvest、去重、简报
- Evaluator 与 next hypothesis 写回 Context

**交付物**：可每日运转的实验助手 MVP。  
**验收**：第 8.3 全条。

### M5 增强（v1）

- SLURM / 远程 SSH Runner 适配器
- OCR PDF、公式感知切分
- 多提案并行消融（资源配额内）
- UI：简报、diff 审批、run 曲线

每阶段可独立回滚：新模块以适配器接入，关闭 feature flag 即退回上一阶段能力。
